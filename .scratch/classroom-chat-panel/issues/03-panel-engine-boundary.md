# G1：面板与课堂引擎的边界行为

Type: grilling
Status: resolved
Blocked by: —

## Question

输入区和历史列表搬进面板之后，"学生的操作"和"课堂引擎的操作"会在同一个面板里相撞。要定的是撞上时的行为：

1. **历史浮层开着的时候，引擎自动开新会话**（讨论邀请、soft-close 续接、切场景自动结束会话）——浮层要不要自动关掉、把学生带回对话？现在是硬切（`PlaybackChromeRoot.tsx:1786` 发送后强制 `switchToTab('chat')`）。注意 P1 已定：历史是**浮层**而不是另一屏，所以学生始终看得见底下的对话，问题从"要不要切屏"缩小成"要不要关浮层、以及浮层下面的对话要不要自动滚动/闪提示"。R1 的调研可作参照：**六个主流 AI 对话产品里找不到"后台推进的会话被自动切前台"的先例**（相邻先例只有站内客服组件 Intercom / tawk.to 的自动弹出，且会把未读清零）。
2. **点"新对话"时当前活着的会话怎么办**——先结束它（`use-chat-sessions.ts:1798-1804` 现在就是这么做的），还是留着让它继续活着（会和单活会话不变量冲突）。
3. **续写一段已结束的旧对话时，导演上下文（`directorState`：轮数、agent 发言记录、白板 ledger）要不要一起带过去**——带，旧对话语境连贯；不带，等于同一段对话里换了脑子。数据结构已支持（`lib/types/chat.ts:304-308` 就挂在会话上），纯粹是产品取舍。
4. **点开一段旧对话时它在不在上课**——单活会话不变量下，点开旧对话会不会把当前正在进行的会话挤掉、以及被挤掉的那段怎么收场。
5. **"停止 / 继续"按钮**（现在挂在展开的会话卡片里，`chat-session.tsx:353-384`）在聊天式 UI 里去哪——保留成消息流里的分隔条与按钮，还是收进别处。

会话开场调 Skill: grilling + domain-modeling。

## Answer

**一句话：面板里"显示中的对话"与"活跃会话"是两件事；抢不抢前台按"谁的动作"判。**

今天的 `activeSessionId` 不是"学生正在看的对话"，而是"最近被谁激活过"：`sendMessage` 新建 QA（`use-chat-sessions.ts:1804`）、讨论开始（`:2007`）、**每个场景的 lecture 会话（`:2108`/`:2156`）**都会改写它，而 lecture 会话又不进对话 tab（`chat-area.tsx:160`）——播放一开始，指针就落在学生看不见的会话上。所以新面板不复用它，另立 `displaySessionId`。

**1. 抢前台的判据是"谁的动作"**
- 学生发起的动作——点讨论邀请的"加入"（`PlaybackChromeRoot.tsx:1036-1045`）、在输入框发消息——→ 切到那一段、关掉历史浮层、滚到底。
- 引擎自己发起的——soft-close 复活（`use-chat-sessions.ts:1805-1816`）、切场景结束活跃会话（`PlaybackChromeRoot.tsx:691`/`:1118`）、lecture 进场——→ 不抢前台，只出未读提示；浮层不自动关。
- 依据：R1 查到的六个主流产品都没有"后台推进的会话自动切前台"的先例；相邻先例只有站内客服组件，而它一弹就把未读清零。

**2. 学生主动换目标时不掐掉正在进行的会话**
- "新对话" = 清空面板 + 焦点进输入框的**纯草稿位**：不落会话、不动活跃会话。今天 `createSession` 直接建一个 `status: 'active'` 的空会话（`:1400`），那样会同时存在两个活跃会话，破坏单活不变量（判据 `isOpenLiveSession`，`:311-315`）。
- 点开旧对话 = 只换显示，活跃会话照旧活着，输入区上方提示"另一端还有讨论在进行 · 回去"。
- 学生在显示中的那段真发消息时，才走 `sendMessage` 既有逻辑：先结束所有活跃 QA/讨论（`:1798-1804`），再复用或新建。两条入口都不会产生"两个活会话"。

**3. 续写旧对话 = 复活那一段会话本身**
- `completed → active`，复用同一个 `sessionId` 和它的 `directorState`（`lib/types/chat.ts:304-308`：轮数 / agent 发言记录 / 白板 ledger），不是"新建一段、把旧消息塞进去"。白板 ledger 不带走的话，agent 会以为白板是空的，可能重画覆盖。
- 今天 completed 会话永不复用（`:1796` 刻意挡掉），所以这条是本次新开的能力，`use-chat-sessions.ts` 的状态机要跟着改。
- "带不带上下文"因此不是产品取舍，而是由入口决定：从旧对话接着问 = 带；"新对话"问 = 天然不带。

**4. 停止 / 继续住输入框上方的一条细状态条**
- 只在存在活跃或 soft-closing 会话时出现；soft-close 带倒计时（"继续"按钮上的 `Ns` 今天就有，`chat-session.tsx:368-381`）。
- 理由：soft-close 是倒计时型动作，藏在长消息流末尾意味着学生得滚到底才看得见。
- 消息流末尾的"已结束"分隔条（`chat-session.tsx:330-347`）保留，但只做状态展示。
- 这会略微扩到 P1 定下的输入区形状（多一行状态条），原型里没画过，S1 定稿前建议补一眼。

**5. 未读只用一个信号**
- 对话 tab 的琥珀点统一表达"那边有值得你看的东西"（未读新内容 或 轮到你了），差异靠输入区上方的文案区分，不做两套视觉：两者的处置动作完全一样。
- 清零时机 = 学生把那一段切到前台显示。历史浮层里的条目只保留"进行中 / 已结束"状态点，不叠未读。
- 今天琥珀点的条件是"有活跃会话、且学生停在笔记 tab"（`chat-area.tsx:163-166`、`:305`），要按新语义改写。
- 全屏时右侧面板被强制收起（`PlaybackChromeRoot.tsx:613-614`），没有 tab 可挂点，信号落在右侧黑框的输入条上。

**6. 被引擎就地结束 = 安静收场**
- 切场景（`PlaybackChromeRoot.tsx:691`/`:1118`）或讨论 soft-close 到点时，学生可能正读着那段：末尾出"已结束"分隔条、状态条里的"停止"消失，输入框照旧可用（接着问 = 复活这段）。不弹 toast、不切显示、不清屏。

**7. 草稿按会话各留一份**
- 内存里的 map，不持久化；"新对话"草稿位独立一份。切走再回来草稿还在。
- 理由：单份草稿有真实危害——学生在 A 打了半句、去浮层翻 B，回来一按回车发给了 A，而心理上以为在 B。
- P1 已定全屏输入条与面板输入框草稿互不共享，这条不变。

**8. `activeSessionId` 拆成两个概念**
- `displaySessionId`：学生正在看哪段，lecture 永远不会是它，可持久化（存放位置见 G2）。
- 活跃会话：语义收窄为"引擎或学生正在推进的 QA/讨论"。
- lecture 不再抢显示，它的记账继续用现成的 `lectureSessionIdRef`（`PlaybackChromeRoot.tsx:548`）；副作用是 `sendMessage` 里 `type === 'lecture'` 的特判（`use-chat-sessions.ts:1796`）可以退役。
- **规格里要逐个核查的消费者**：`getActiveSessionType()`（`PlaybackChromeRoot.tsx:1912`，全屏停止按钮靠它判断在跑什么）、`retireActiveLiveRequest(activeSessionId)` 的 effect（`use-chat-sessions.ts:2075`）、`expandedSessionIds`（卡片展开状态随卡片一起消失）。

**9. 列表去掉逐条时间戳**
- 只留"今天 / 昨天 / 更早"分组标题，精确时间放 hover `title` 兜底。R1 六家一致，分组已经表达了粒度。
- 这条推翻了地图待定区原先的"按保留处理"。

**10. 讨论邀请卡留在原位**
- 它经 portal 渲染、锚在发起讨论的 agent 头像旁（`roundtable/index.tsx:267-270`、`:988`、`:2046`），不在 P1 撤走的"麦克风 / 气泡按钮 / 用户头像"里；引擎会停在 `currentTrigger` 上等学生点（`lib/playback/engine.ts:264-270`、`:347-349`）。
- 规格里把它**显式登记为"舞台侧保留物"**，与 3 秒紫色气泡并列：舞台侧的对话可视化一律保留。不搬进对话面板——学生可能正停在笔记 tab，搬进去会让引擎干等一个看不见的邀请。全屏时经 `portalContainer` 渲进全屏容器（`:1113`），保留。

**11. 消息流贴底才跟随**
- 学生视图在底部 → 新内容自动跟随；学生手动上翻过 → 不跟随，底部浮出"有新内容 ↓"小按钮，点了回到底部并恢复跟随。

**对 S1 的交待**
- 1、2、4、5、6、7、8、11 写进规格的结构与 props 层（`displaySessionId` 从哪来、状态条长什么样、未读怎么算、滚动跟随挂在哪）。
- 3 是一条真正的状态机改动（复活已结束会话）。
- 9、10 是观感与登记项。
- 4 与 11 涉及原型没画过的画面（输入区状态条、"有新内容 ↓"），定稿前值得在原型里补一眼。
