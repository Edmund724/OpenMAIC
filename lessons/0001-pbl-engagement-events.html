PBL engagement 事件账本：每个事件如何被定义

对应报告 §3.1-A · 核实于当前 main（2026-09-20） · 速查表：reference/pbl-engagement-events.html

你点名的核心问题是："学生独立掌握某概念"这种事件，系统凭什么判定它发生了？答案是理解整个采集层的一把钥匙——OpenMAIC 对每种事件的"定义方式"分三类，而"谁有资格定义"比"定义内容"更能体现设计思想。学完本课，你应该能给每个事件说出：谁记录、什么条件、payload 是什么、谁消费。

1全景：四类数据源（报告 §3.1）

数据源一句话粒度

B经典课堂聊天stateless，每条消息捎带完整现场快照消息 + 课件状态

A 是"学习行为"数据，D 是"系统运行"数据——两者是 PBL project 上两套独立的环形账本（各 500 条上限），但落库时写进同一张 runtime_records 表，靠 payload 里的 kind: 'pbl_engagement_event' | 'pbl_runtime_event' 区分（lib/pbl/v2/runtime/record-payloads.ts:48-60）。B/C 走同两张表的不同 session kind。

2账本本体

// lib/pbl/v2/types.ts:216-226
{ id, kind, microtaskId?, milestoneId?, ts, payload? }

追加式、环形缓冲 500 条（MAX_ENGAGEMENT_EVENTS，kernel/engagement.ts:28）。每条事件都挂在具体 microtask/milestone 上，自带时间戳——耗时、序列、每任务密度都能事后算出。

3关键框架：三类生产者

"事件如何被定义"在 OpenMAIC 里没有统一答案，而是按谁有资格判定分成三类。这是全课最重要的一张表：

生产者事件定义权在
runtime 确定性代码learner_turn、microtask_opened/completed代码：发生了就是发生了
LLM 主动判断（Instructor 调 record_observation）observation_error / _struggle / _questionprompt：schema 描述 + "use sparingly"
代码按规则判定observation_concept_unlocked、proficiency_changed确定性判据：提交通过 / tier 迁移
设计原则越影响"学生状态"结论的事件，越被移出 LLM 的自由裁量。"掌握概念"曾是 LLM 判断，现在改成了代码判据——这正是你点名问题的答案，下面专节展开。

4逐个事件：定义与出处

4.1 learner_turn — runtime 记"量"

// lib/pbl/v2/agents/instructor.ts:1345-1349（调用 LLM 之前）
recordEvent(project, 'learner_turn', {
  microtaskId: microtask.id, milestoneId: milestone.id,
  payload: { chars: userMessage.length },   // JS 字符串长度（UTF-16 code unit）
});

学生每发一条消息记一条，无 LLM 参与。这就是论文里 MsgNum/MsgLen 的开源对应物——论文用 log(消息数) 和 log(消息字符数) 与模块测验成绩做相关分析，发现显著正相关（MAIC.md §5.2，Table 3）。Simulator（角色扮演场景）侧同样记录（simulator.ts:477）。

4.2 observation_error / struggle / question — LLM 记"质"

Instructor agent 只有两个记录类工具，record_observation 是其一（instructor.ts:1423-1470）。它的"定义"写在两个地方，全部原文照录：

① 工具 description（给模型看的行为说明）：

"Record a notable learning event mid-task (error, struggle, question) for the evaluator. Analytics only — this does NOT advance the task or gate completion. Use sparingly, for moments worth showing the evaluator."

② 参数 schema 的逐字段 describe（lib/pbl/v2/operations/runtime/schemas.ts:62-91）：

kind: 'error'    → "learner hit a real bug worth tracking"
      'struggle' → "learner is stuck longer than expected without an explicit error"
      'question' → "learner asked a substantive, non-routine question"
signature → "Short stable MACHINE tag ... so duplicates can be deduped
             (e.g. 'undefined_variable', 'off_by_one').
             This is never shown to the learner — use label for the human-readable name."
label     → 可选，≤60 字符，人类可读，用学生的内容语言
note      → 可选，≤500 字符，"quoting / referencing the learner action that justifies this observation"

③ system prompt 里的唯一规则（lib/pbl/v2/prompts/instructor-base-rules.md:232-234）：

"You may call record_observation when something analytically interesting happens (a recurring error, a sticky struggle, a substantive question). It is for the evaluator only — it does NOT advance or gate anything. Use it sparingly, not on routine turns."
注意节流完全靠 "use sparingly" 这句软约束，代码里没有任何频率/冷却限制。LLM 判定的质量标准就是上面三句话——"值得给评测者看的时刻"。你自己的系统若照搬，要想清楚是否接受这种模糊性。

4.3 observation_concept_unlocked — "掌握"的定义（重点）

报告里写"Instructor agent 观察到学生独立掌握某概念"——这已经过时了。当前代码的真相分三层：

现状（唯一生产者）：提交评测通过（≥60 分）后，由前端提交流程的确定性代码写入，signature 固定为 submission_passed_<taskId>（components/scene-renderers/pbl/v2/submission.tsx:544-561）。也就是说，当前"掌握"的 operational definition 是"该任务的作品通过了自动评测"——可复现、可单测，但粒度粗：它只认"任务完成"，不认"对话中表现出的领悟"。

历史痕迹：record_observation 的 kind 枚举里曾经接受 concept_unlocked，现已移除（schemas.ts:64 只剩 error/struggle/question）。两处化石可以佐证旧设计存在过：

  • tier-guidance.ts:61 的 beginner 档指引仍写着 "record concept_unlocked and advance"——与工具 schema 矛盾的过时 prompt 文本（模型照做会收到 schema 校验错误）；
  • instructor.ts:985 的 stripLeakedToolJson 正则，专门清理助手文本里泄漏的 {"kind":"concept_unlocked|error|struggle|question",...} JSON——说明旧版让模型用裸 JSON 记录观察，后来才改成正式工具。

论文版（未开源）：论文 3.2.1 的"掌握"由对话采集 agent + summarization agent 从自然对话中抽取学术特征，组织成结构化标签画像（MAIC.md:152-154）。这条路在开源版整条缺失——所以"对话中显露的理解"这个信号，当前代码无处可记。

对你造系统的启示OpenMAIC 的演进方向是：影响状态的判定，从 LLM 自由裁量退到确定性判据。代价是信号粒度变粗。如果你需要"对话中掌握"这种细粒度信号，要么恢复 LLM 判定并加上校验/去重机制，要么像论文那样做独立的采集 agent——两种路线都要直面"LLM 判定不可靠"这个问题（OpenMAIC 的选择是：LLM 只负责无关痛痒的 analytics，状态判定全归代码）。

4.4 microtask_opened / completed — runtime 记任务生命周期

全部由确定性代码触发：opened 在任务 todo→in_progress 时（progress.ts:452,548,792），completed 在 advanceMicrotask 时带 { reason }（progress.ts:509-513；reason 如 "Latest task submission passed evaluation (87/100)."）。两个事件的时间戳之差就是任务耗时——耗时是算出来的，不是埋点埋出来的。microtask_skipped 类型还在但无任何生产代码写入（遗留）。

4.5 proficiency_changed — 代码记状态迁移

唯一写入点是 proficiency 引擎的 emit()（dynamic-signals.ts:58-82）：tier 发生迁移时记录 { from, to, reason, score, confidence }。注意 adjust_difficulty 工具本身不写事件——它只是把学生明说的难度要求（"太难了"、"我是初学者"，任意语言）转成 explicit override，绕过 EWMA 直接锚定 tier；只有当这导致 tier 实际变化时，才由 emit 留下这条事件。

4.6 遗留类型：closing_check / stage_synthesis_check

schema 还在（schemas.ts:19-57），但工具已移除、无生产写入。其中 stage_synthesis_check 的 schema 里留着全库最后一句"自发表述"判定的痕迹："If the learner had already articulated the concept spontaneously (the escape hatch — you did not need to ask), quote that articulation here."（schemas.ts:49）——旧设计里"主动说出"和"被问出来"是有别的，这个新设计里也没有了。聚合层 closingQuality 对新数据恒为 undefined。

5signature：LLM 命名、代码判重

signature 是 LLM 自由生成的机器标签（schema 只要求非空字符串，给例子 'undefined_variable'），不是枚举。判重分两层：

  • 记录时（instructor.ts:1434-1446）：同 microtask 下已有同 signature 的 error → 标记 repeatedError=true，proficiency 按 −0.7（而非首次的 −0.4）计；
  • 聚合时（kernel/engagement.ts:143）：repeatErrorCount = error总数 − 去重signature数。
隐患signature 靠 LLM 命名的一致性去重——同一个错误这次叫 undefined_variable 下次叫 undefined-var 就漏判了。这是"自由文本做 key"的经典陷阱，你自己的系统可以考虑给 signature 做枚举约束或嵌入归并。

6下游：事件如何变成数字

聚合函数 microtaskEngagement（kernel/engagement.ts:67-153）把账本折成 PBLEngagementSummary（时长、轮次、错误/重复错误、signature 列表、解锁概念），喂给 milestone 评测 prompt 和披露阶梯的 stuck 判定。proficiency 引擎则按固定分值把事件转成分数（proficiency.ts:484-522）：

事件direction说明
error 首次 / 重复−0.4 / −0.7重复错误罚得更重——"讲了还错"是更强的信号
struggle / question−0.5 / −0.3提问也是负向信号（求助意味着没独立做出）
concept_unlocked+0.5唯一的正向观察信号
newScore = clamp(0.2 · direction · weight + 0.8 · score, −1, 1)   // EWMA，α=0.2
// proficiency.ts:711-726；门控：confidence≥0.4、≥3 信号、距上次换档 ≥5 个 learner turn

方向分和权重全部硬编码，LLM 只负责把观察分类成 kind + signature。这就是报告 §4.4 说的"LLM 观察、代码计分"分离：数字演进完全确定、可复现、可单测。

7论文对照：这套采集支撑什么、缺什么

论文 §5.1 / §5.2 论文用课堂日志做了两类分析：① MsgNum/MsgLen 与成绩的相关（MAIC.md:341）——开源的 learner_turn{chars} 正是为此准备的数据；② 七类行为分类（提问/发起想法/回应/协商验证/调节 AI 角色/调节课堂进程/分享情感，MAIC.md:326）——开源版没有任何行为分类代码，事件账本只覆盖了"错误/卡壳/提问"三个偏向困难诊断的维度。另外论文 3.2.1 的画像管线（对话采集→结构化标签）整体缺失，所以事件数据的"画像出口"在开源版只有 proficiency 单轴。

8带走：六条可借鉴的设计决策

  1. 按"判定资格"分层：事实类事件归代码，诊断类事件归 LLM（且声明 analytics-only、不门禁任何流程），状态类判定归确定性规则。
  2. LLM 观察、代码计分：让 LLM 做它擅长的（从对话认出"这一刻值得记"），数字演进全部确定性——可复现、可回归测试。
  3. 事件即时间序列：opened/completed 成对 + 时间戳，耗时等派生指标事后算，不冗余采集。
  4. signature 机器标签 + 判重：让"同一个错误反复犯"成为一等信号（−0.4 → −0.7），但要警惕自由文本 key 的漂移。
  5. analytics 与流程解耦：record_observation 明确 "does NOT advance or gate anything"，记录失败不影响学习流程。
  6. 明确不采集什么：翻页、停留时长、逐题用时、光标——全是刻意留白，复杂度和隐私的主动取舍。
